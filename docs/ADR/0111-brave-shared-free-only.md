# ADR-0111: Brave shared provider-enforced free-only admission

## Status

Proposed, local implementation. Independent review, integration, key binding and explicit ledger activation remain separate. No real account identifiers, credentials or dashboard evidence are committed here.

## Context

The owner requested repair of Brave free-credit records and explicitly permits only free Brave/Tavily use. One account key does not establish repository-exclusive use. ADR-0090 v1 therefore remains unavailable when exclusivity is unproved. A plan-wide provider-enforced free-only limit can protect shared consumption without pretending the project can observe or reserve other applications' requests.

[Official FAQ](https://api-dashboard.search.brave.com/documentation/resources/help-feedback) distinguishes existing postpaid charging from prepaid credits and describes plan usage limits. Neither zero out-of-pocket usage nor a rate-limit header proves free-only enforcement. The actual account must show the enabled, saved free-only limit, its application to all keys on the identified Search plan, and provider refusal of usage beyond that limit. Do not infer a paid input's meaning from a dollar amount or migrate the account to another plan.

## Decision

Add a distinct `brave-budget-v2` ledger and `provider_enforced_free_only` grants. Preserve the exact v1 exclusive-key validation, fields and interpretation. No automatic conversion, mixed grants, overwritten history or alternate ledger branch is supported.

A v2 grant has exactly: `id`, `keyId`, `scope`, `source`, `evidenceSha256`, `accountPlanBindingSha256`, `verifiedAt`, `expiresAt`, `protectionEndsAt`, `requestLimit`, `freeOnlyEnabled`, `hardStopConfirmed`, `plan`, and `accountObservation`. The initial supported plan is `search_postpaid`; source is `owner_dashboard`. Both free-only and hard-stop assertions must be true. Hashes bind independently reviewed private evidence and account/plan/key association; syntactic hash validation is not a live provider check or proof that evidence is genuine. Do not prepare real hashes until evidence and key binding are verified. For `accountPlanBindingSha256`, hash UTF-8 `JSON.stringify([accountStableId, planStableId, keyId])` in that exact order; use verified service identifiers unchanged and the actual 16-hex key fingerprint. Keep the account/plan identifiers and canonical input private. This stable binding excludes observation time, usage and settings snapshots. `evidenceSha256` separately hashes the reviewed private evidence for this verification and may change on renewal.

The account observation has exactly `source`, `observedAt`, `requestsUsed`, `usageCostUsd`, `outOfPocketCostUsd`, and `monthlyFreeCreditUsd`. It must be contemporaneous with verification, show zero out-of-pocket cost and positive remaining observed free credit. USD observations are two-decimal strings, not exact billing totals or an exchange-rate conversion. Never infer project history from account usage or invert rounded dollars into request counts.

Each grant allows at most 950 recorded project reservations. The existing 950/31-day recorded-reservation counter spans all grants and all four consumers, including manual execution. The provider's plan-wide hard limit, not that project counter or an account snapshot, prevents shared applications from entering paid usage. Other applications may exhaust availability sooner. Summary exposes project remaining requests, dated account observation and `providerRemainingRequests=unknown`; v2 never claims `remainingVerifiedRequests` as an account balance. Expired/held grants are not current eligibility even if their numeric project remainder is positive.

`expiresAt` must be after verification, within 31 days, and no later than the independently reviewed `protectionEndsAt`. That boundary may be deliberately earlier than an ambiguous displayed billing date; it is not a fabricated billing timezone or exact period end. No clock or calendar inference renews evidence. Continue the monotonic 30-second dispatch deadline and trusted server-time expiry margin. Changes in the key, plan binding, evidence, free-only protection or an uncertain provider state require a new review or hold, not automatic refresh.

Initialization is explicit `--initialize-shared --grant-file <private-file>` and create-only on the existing `brave-usage-ledger` branch. It records `recordingStartedAt` from the authoritative initial GitHub 404 Date and `historyBeforeRecording=unknown`. Empty recorded entries mean only no entries since recording began. A 404 alone does not prove a ledger never existed: operators must establish first initialization, never recreate deleted history. Existing v1 or v2 state refuses initialization. Further grants use the existing append-only activation path; key/account-plan rotation is refused.

The narrow v2 supersession of ADR-0090 and the corresponding Operations/Data Sources wording is: exclusive repository ownership and known global remaining requests/history are not required for fee protection when the reviewed provider-enforced free-only plan protects every request. Unknown pre-recording history remains explicitly unknown and is not invented, imported or reset. All v1 requirements remain unchanged. Pending requests, unknown outcomes, invalid evidence, expiry, invalid/corrupt/missing state and quota rejection still hold. This exception does not weaken Tavily, paid budgets, consumer inventory, source quality, no-retry or publication rules.

## Reviewed dashboard-login binding alternative (v3)

The owner-requested repair may use `brave-budget-v3` when the official dashboard exposes no stable service account/plan IDs. This is a distinct `verified_dashboard_login_and_plan_key` protocol, not a claim that a login email or plan label is a service ID. v1/v2 semantics remain unchanged; no conversion or mixed-version grants are allowed.

The reviewer must observe the authenticated personal login identity, the Search postpaid plan listing the actual key, and that plan's saved all-Search-keys free-only hard stop in the same private review. The actual key fingerprint must match the production diagnostic. A display name, key name alone, dollar balance or hash syntax is insufficient. Ambiguous account, multiple/unmatched keys, plan ownership or protection remains hold. Do not probe undocumented APIs or hidden application state to manufacture identifiers.

v3 retains all v2 grant fields and additionally requires exactly `bindingType=verified_dashboard_login_and_plan_key`, `loginIdentityVerified=true`, and `planKeyAssociationVerified=true`. `accountPlanBindingSha256` hashes UTF-8 `JSON.stringify(["brave-dashboard-login-plan-key-v1", verifiedLoginEmail, "search_postpaid", keyId])`; retain the verified displayed login email unchanged, without lowercasing or other normalization. It is an account locator, not an immutable identifier. Keep the canonical identity input private. The separate evidence digest covers the dated login/plan/key association and saved protection observations. Any login identity, key or plan change requires hold; renewal cannot rotate the binding. Hashes attest reviewed evidence, not live provider verification.

Every v3 grant is limited to **50 project reservations and 24 hours**, also no later than the independently reviewed protection boundary. No automatic renewal. The existing 950/31-day counter, durable pending debt, quota hold, trusted-clock dispatch margin, all consumers, create-only branch and unknown pre-recording history remain unchanged. The lower project ceiling is not an estimate of provider remaining free requests; financial protection still depends on the verified plan-wide hard stop.

Explicit first initialization uses `--initialize-shared-login --grant-file <private-file>` only after the same genesis review. Existing v1/v2/v3 branches refuse it. The connector-only creation route described in Operations must construct and validate the identical v3 contract; deployment alone does not activate any ledger or authorize a search. This narrow alternative supersedes only the requirement for opaque service identifiers in the v2 binding procedure, not the actual account/plan/key association or free-only enforcement.

## Private-proof separation prototype (v4, inactive)

After public account-metadata publication was refused, the owner chose continued suspension while a private-proof route is developed and tested. No actual account record may be re-uploaded through another route. v1–v3 remain unchanged; this prototype neither migrates a ledger nor initializes one, provisions secrets, changes workflow permissions or authorizes public data transmission. The later owner-approved step wiring below is a narrow deployment addition, not permission to publish private evidence.

`brave-private-proof-v1` is private: fixed repository/branch, randomly generated ledger identity, exact recording start, full v3 grants and a CSPRNG-generated 256-bit commitment nonce. `prepareBravePrivateProof` is an offline preparation helper; real use requires separately approved private storage. Do not choose a human-readable nonce, expose it in logs or put the proof in repository files/artifacts. The owner subsequently authorized a repository Actions secret named `BRAVE_BUDGET_PRIVATE_PROOF` and step-only injection into the five existing main production workflows listed in Operations. Code wiring does not create that secret or initialize a ledger. Actual saved state remains separately verified; the JSON size bound is not a claim that the secret store accepts that size. Repository-secret access cannot be enforced per step: a person able to edit trusted workflows may expose the value, a trust boundary disclosed to the owner. The Free refresh workflow's exact secret inventory adds only this approved proof name; its paid-provider prohibitions, manual/main-only scope and all other assertions remain unchanged. The Epoch integration also pins the exact new production-job hash, while retaining both previous hashes after removing only the single approved proof env line; the candidate job remains secret-free.

Public `brave-budget-v4` permits only schema, random ledger identity, proof commitment, recording start/unknown prior history, project grant IDs/admission times/expiry/caps, project reservation receipts without key IDs, and hold state. No account observations, plan, key fingerprint, evidence hash or account binding hash is permitted. The commitment is HMAC-SHA256 with the private random nonce as key and `brave-private-proof-commitment-v1\n` plus recursively key-sorted JSON of the remaining proof as message. It binds the complete immutable private proof without publishing a reusable identity digest or an email-guessing oracle. It is not encryption: disclosure of the private proof/nonce defeats that privacy assumption. Public project times/counts still reveal project activity, and publication needs its own approval; do not call the entire record anonymous.

The adapter verifies exact destination, ledger identity, recording time, commitment and complete grant projections, then reconstructs v3 only in memory for the existing gate. Every write uses explicit public allowlists. A changed private identity cannot silently reassign old public entries because its commitment no longer matches. Full v3 summaries contain private information and must not be logged or emitted as artifacts; the v4 adapter has no CLI that emits them. The ordinary public status CLI rejects v4 rather than exposing hydrated state. Missing or changed private configuration, wrong ledger/key, evidence mismatch, expiry and unknown outcomes remain hold. Cached runtime configuration is rechecked on each call, including after asynchronous setup.

Initial scope is a fixed proof: **no renewal, proof rotation, migration or automatic initialization**. All 50/24h, 950/31-day, CAS, pending-debt and dispatch protections run through the existing gate. At expiry remain suspended; future renewal requires a separately reviewed continuity protocol that cannot replace old proof/ledger history. No existing ledger may be recreated under a new random ID. A projection alone proves neither first initialization nor provider free-only protection.

Offline tests cover private-field leak scans, wrong destination/creation time/identity, commitment changes, malformed proof, config removal, concurrent last allowance, pending debt, quota hold and receipt-write failure. Only synthetic fixtures are used. Actual private storage, publication approval, initialization and natural-run acceptance are not completed by these tests.

## Explicit private-proof continuity (inactive until separately executed)

The November 18 implementation narrowly supersedes the initial no-renewal API restriction, not the evidentiary or activation boundaries. It retains private-proof-v1 and public-budget-v4 formats and the unchanged production adapter. No runtime, CLI, schedule, workflow, secret setup, provider request or actual ledger operation is added. Code delivery alone does not restore service.

`prepareBravePrivateRenewal` prepares a next private proof offline. `renewBravePrivateProof` explicitly performs one public-store CAS using both complete old and next private proofs. Identity, nonce, destination, recording time and the complete canonical old grants must be identical. Exactly one grant is appended: fresh independently reviewed evidence, same key/account-plan binding, no greater per-grant allowance, at most 50 requests/24 hours and no later than the reviewed protection boundary. A changed evidence hash is only a structural check, not proof of authenticity or live account settings. No account observations or private fields are published.

All old grants must have expired, including conservative server-clock precision, before renewal. The new observation must follow every old expiry and finished receipt. Pending receipts, quota holds, unknown/skewed clocks, malformed snapshots, overlapping grants, identity rotation and changed prior evidence all refuse. The new observation must already be effective at the earliest plausible server/local time, and the new grant must retain a full dispatch margin. Reservations, receipts, unknown pre-record history and the 950/31-day count are preserved, not reset. A newer account screenshot cannot settle an unresolved request or clear a hold.

Before public CAS, the successor must fit 48,000 UTF-8 bytes in compact `JSON.stringify` encoding, conservatively below the [GitHub Actions 48 KB secret limit](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets). Store that exact compact encoding with no added whitespace or newline; this size check does not prove secret-write permission or successful storage. When full, stop rather than truncate grants, split secrets or create an alternate storage route.

Operational cutover requires privately retaining the complete old proof (including nonce), next proof, and the immutable public head before doing anything. GitHub Actions secrets cannot be read back through its API; if the old proof has no approved recoverable private copy, stop rather than recreate a ledger or invent a nonce. After renewed evidence/key binding and required approval, use the helper for one ledger CAS, then replace only the existing private proof secret. Secret-first also fails closed: only the exact matching proof/ledger pair can admit calls. Between phases service remains unavailable. Old in-flight clients cannot rewrite a later ledger because the non-force CAS rejects stale heads, and renewal refuses pending debt. No new permissions are required by the code.

On CAS conflict, missing acknowledgment or transport error, do not retry automatically, replace secrets blindly or assume nothing happened. Read the authoritative public head and compare its commitment, grant prefix and complete receipts privately against the retained expected projection. An acknowledged write only proves the ledger phase, not secret cutover or provider availability. A secret rollback cannot roll back public accounting; never reset the public branch to undo a grant. Recover by completing the same validated cutover only after resolving uncertainty, or leave the mismatch suspended. Neither the HMAC nor the helper protects against an administrator deliberately rewriting both the private proof and public history, or force-resetting the branch; trusted repository administration remains a disclosed assumption. The helper return does not establish continued eligibility, and no source-use scope or approval check is superseded. Both published sites and Git history are publicly reachable, not assumed private intranets. Actual use still requires verified account-wide hard-stop protection and applicable source-use authorization; operational approval is not conferred by this ADR or synthetic tests.

Offline tests cover preserved receipts and private-field exclusion, old/new secret mismatch in both orders, stale-client CAS, concurrent renewals, unknown write outcome, immutable prefix/nonce/binding, expired evidence, clocks, pending/held debt, caller mutation and the complete rolling 950-reservation ceiling through the unchanged v4 runtime adapter.

## Key-binding diagnostic

The existing manual Tavily status workflow gains an explicit `operation` choice. Default remains `tavily-status`; the isolated `brave-key-fingerprint` job runs only on main with exact `github.sha`, read-only contents and non-persistent checkout credentials. Only its diagnostic step receives `BRAVE_API_KEYS` and `BRAVE_API_KEY`. This is an explicit new secret-consuming step requiring independent review; no provider, ledger, package installation or generation command is run.

The offline `review:brave-budget -- --key-fingerprints` mode splits newline/comma/semicolon, trims and deduplicates each variable, then emits only SHA-256 first-16 fingerprints, counts, missing flags and their combined set. Internal whitespace is refused because the CEO consumer splits additional whitespace; ambiguous production parsing must not be attested as equivalent. No raw key, prefix, suffix, length or exception object is logged. Workflow dispatch and private browser comparison are separate operational steps; code delivery does not perform them.

## Consequences and validation

The shared mode trades an impossible claim of account-wide local accounting for an explicit provider-enforcement dependency. Evidence is a dated reviewed snapshot, not permanent access to settings. Do not claim continuous revalidation without an actual supported mechanism; if protection changes or becomes unknown, stop. New months never clear reservations, pending debt or quota holds, and grant renewal never refunds history.

Offline regressions cover strict v1/v2 separation, missing evidence, unknown versus zero history, cross-grant caps, key/account binding, durable failures, CAS uncertainty/races, clock expiry, actual consumer transports, create-only initialization and isolated secret diagnostics. All test transports are synthetic; the free-search suite installs a rejecting default fetch guard. Full repository checks and independent actual-diff review remain mandatory. No new workflow, provider request, paid call, production-data edit or real evidence fixture is authorized by this ADR.


## One fixed private manual canary (separate from business restoration)

The owner authorized an independently reviewed main-only manual job using the existing original Actions proof and production key, plus a separate private repository secret `BRAVE_BUDGET_RENEWAL_CHAIN`. This narrow addition does not replace the original proof, expose its contents, automatically renew, open the five business workflows, change payment settings, create a GitHub Environment or establish new administrators. The original proof remains stored unchanged. The operator retains the independently verified supplement privately, so the successor can be reconstructed from original + supplement without printing the original. Actual permission to prepare and store private material must precede that step; this document is not itself authorization.

The single-test job requires a successful read-only preview job in the same workflow, then revalidates everything itself. Job identity forces preview mode even when the selected workflow input is single-test. The only workflow inputs are `operation=preview` (default) and `operation=single-test`. Both check out `github.sha` with nonpersistent credentials, use only the fixed Node entry point, and require authenticated Actions, this repository, main, workflow_dispatch, exact workflow identity and equality of private reviewed dispatch SHA, workflow SHA, execution SHA, actual checkout and live main. There is no arbitrary command/query/ref input, schedule, debug, installation, artifact, summary or business generator. Preview has read-only GitHub permissions and a write-refusing store; it authenticates the original proof against the fixed historical public ledger, checks the fresh supplement, and runs the existing renewal checks against an in-memory sink. It makes zero Brave requests and zero public ledger writes. Passing preview does not prove the account settings remain unchanged or that later CAS will succeed.

`single-test` alone has project-scoped ephemeral `contents: write` for the existing shared accounting branch. This permission is repository-wide at the token level, not a platform-enforced single-branch permission; the reviewed fixed code constrains the writes. Trusted workflow/repository administrators remain part of the boundary. There is no use of a new personal token. The job appends only the fixed successor from the frozen public root. Its ordinary per-grant cap is unchanged, not reduced to 1. A dedicated store interlock admits at most one reservation for the single fixed grant ID across processes, re-dispatches, concurrency, failures and retry. Any existing reservation, whether pending, succeeded or failed, permanently consumes this canary authorization. CAS conflict or uncertain reservation throws without admission retry. Neither a different supplement nor a different run ID grants another slot. The existing shared budget enforces the normal clocks, pending debt, hold, grant and rolling project limits. The dedicated `brave-renewal-smoke` consumer is manual-only and supported only for this fixed grant ID, at most one row, in the login-bound v3 / private v4 path; v1/v2 and existing business consumers retain their behavior.

If renewal CAS acknowledgment is lost, stop that run. A later explicit run can authenticate the exact successor against the same retained original and supplement and continue only if no canary reservation exists. A lost reservation acknowledgment may have spent the one shot: do not retry it, refund it or erase it. If provider completion or receipt settlement is unknown, retain debt. Even a provider success does not count as completed until a fresh authoritative read proves the dedicated receipt is settled successfully for this run. A public ledger rollback, changing both private proofs, or malicious workflow administration is not prevented by this helper; never do these to repeat a test.

The query is the fixed ordinary phrase `solar eclipse`, containing no user or project information. One News Search HTTP request uses the production key, no retry, no redirect or key fallback. A bounded response is validated only in transient memory then discarded; results, titles, snippets, links, headers, exception text and credentials are never logged or persisted. Output is only a fixed ready/finished/refused-or-uncertain enum. The public branch retains only the already-approved project accounting projection. This is a transport/accounting smoke test, not news quality acceptance, business availability or permission to retain/redistribute search content.

### Private supplement preparation and trust

`BRAVE_BUDGET_RENEWAL_CHAIN` must be a compact JSON string below 48,000 UTF-8 bytes, with exactly these top-level fields. The placeholders below are **not usable evidence**, and must never be promoted by copying a prior observation or changing a timestamp:

```json
{
  "schemaVersion": "brave-renewal-chain-v1",
  "purpose": "brave-private-renewal-single-canary-20261118",
  "baseHead": "5c9b8d129bcd188b98aeeeac25840a0f3acfe169",
  "approvedDispatchSha": "FINAL_INDEPENDENTLY_REVIEWED_CURRENT_MAIN_SHA",
  "freshKeyId": "INDEPENDENT_CURRENT_DASHBOARD_KEY_FINGERPRINT",
  "freshAccountPlanBindingSha256": "INDEPENDENT_CURRENT_LOGIN_PLAN_KEY_BINDING",
  "grant": "COMPLETE_FRESH_V3_GRANT_OBJECT_NOT_A_STRING"
}
```

The nested `grant` uses the exact v3 fields defined above. Its ID is fixed to `81d366bc-2d48-4a18-a716-a8eb722ef57a`; requestLimit equals the original latest grant limit (no increase or decrease). Verification must be independently observed after every previous expiry and completed receipt, and expiry/protection boundary must follow that observation within the existing 24-hour limit. No pending debt is reconciled by a screenshot. The grant's fingerprint/binding must equal both fresh top-level values and the original private proof's binding; the runner independently fingerprints the actual single configured production key. The new evidence digest must be distinct and backed by the actual new review. Missing facts cause refusal; do not fill a key name, old log, old hash or estimated account balance as fresh evidence.

An independent reviewer or the owner must obtain the actual key in the authenticated Dashboard and compute its SHA-256 over unchanged UTF-8 locally, using only the first 16 hexadecimal characters as `freshKeyId`. If the Dashboard exposes no non-secret fingerprint, a masked label cannot establish the match. Do not send the real key to a chat, repository, workflow input, screenshot, log or web hashing service. Use an approved local private tool or masked local input, not a shell command containing the secret. Compute `freshAccountPlanBindingSha256` over UTF-8 `JSON.stringify(["brave-dashboard-login-plan-key-v1", verifiedLoginEmail, "search_postpaid", freshKeyId])`, preserving the authenticated displayed email exactly. Real input and its derived hashes remain private. Verify the saved all-Search-key free-only hard stop, contemporaneous usage and plan-key association in the same authenticated review; derive `evidenceSha256` from the retained private canonical observation record. A syntax-valid hash is not proof of a dashboard fact.

The independent review pins `approvedDispatchSha` only after the exact candidate and its integration on main were reviewed; it must be the actual current main dispatch SHA, not an arbitrary user-provided public input. The private record is a trusted attestation, not self-authenticating data. The runner can verify consistency, cryptographic binding and accounting state, but cannot remotely certify an unverifiable Dashboard observation. Repository secret writers and trusted workflow administrators can replace attestations; code does not claim to protect against them. Keep the review provenance privately and refuse configuration when it cannot be established. Preview and single-test use the same complete private record. If main advances, re-review the changed code and update only the reviewed SHA in the private record; this does not change the fixed grant or restore a consumed slot. Do not publish real evidence, identity, key fingerprints or account-derived digests even in a nominally public "approval manifest".
